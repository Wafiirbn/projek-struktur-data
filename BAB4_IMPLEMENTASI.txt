BAB 4
IMPLEMENTASI


4.1  Detail Implementasi Tiap Struktur Data

Sistem Log Monitoring yang dibangun dalam proyek ini mengimplementasikan tiga
struktur data utama secara paralel dan sinkron, yaitu Singly Linked List, Binary
Search Tree (BST), dan Hash Table. Setiap entri log yang diterima sistem langsung
didistribusikan ke ketiga struktur data tersebut sekaligus melalui kelas LogManager,
sehingga masing-masing struktur dapat dimanfaatkan sesuai keunggulan karakteristik
operasinya masing-masing.


4.1.1  Singly Linked List (LogLinkedList)

Linked List diimplementasikan menggunakan pasangan struct LLNode dan kelas
LogLinkedList. Setiap node menyimpan satu objek LogEntry dan satu pointer ke node
berikutnya (next). Kelas LogLinkedList memelihara dua pointer, yaitu head yang
menunjuk ke node pertama dan tail yang menunjuk ke node terakhir, guna memungkinkan
operasi penyisipan di akhir list tanpa traversal.

a.  Operasi Insert (O(1))

Setiap log baru selalu disisipkan di posisi paling akhir (tail) dari list. Dengan
adanya pointer tail, operasi ini tidak memerlukan penelusuran seluruh list sehingga
kompleksitas waktunya konstan O(1). Urutan kronologis penyisipan log terjaga secara
alami dalam struktur ini.

b.  Operasi Search (O(n))

Pencarian pada Linked List bersifat linear karena tidak terdapat indeks atau kunci
pengurutan. Seluruh node ditelusuri satu per satu dari head hingga tail. Terdapat
tiga varian pencarian yang tersedia:

    (1) searchByLevel — membandingkan field level setiap node dengan nilai yang
        dicari.
    (2) searchByModule — membandingkan field module setiap node.
    (3) searchByTimeRange — mengonversi batas waktu pencarian ke format Unix epoch,
        lalu membandingkan nilai epoch setiap node untuk menentukan apakah masuk
        dalam rentang yang ditentukan.

c.  Operasi Delete (O(n))

Penghapusan log usang dilakukan dalam satu kali penelusuran penuh. Setiap node yang
memiliki timestamp lebih awal dari waktu cutoff dihapus secara langsung dengan
memanipulasi pointer antar-node. Penanganan khusus diterapkan pada kondisi head dan
tail untuk menjaga integritas list.

d.  Operasi Statistik (O(n))

Fungsi statistics() melakukan satu kali traversal untuk menghitung frekuensi
kemunculan setiap kategori level log. Hasilnya disimpan dalam unordered_map dengan
kunci berupa nama level dan nilai berupa jumlah kemunculannya.


4.1.2  Binary Search Tree (LogBST)

BST diimplementasikan menggunakan pasangan struct BSTNode dan kelas LogBST. Kunci
pengurutan yang digunakan adalah nilai Unix epoch (bilangan bulat 64-bit) yang
dikonversi dari field timestamp setiap log. Konversi ini hanya dilakukan sekali dan
disimpan dalam cache field _epoch pada struct LogEntry.

a.  Operasi Insert Iteratif (O(log n) rata-rata)

Implementasi insert menggunakan pendekatan iteratif, bukan rekursif, guna mencegah
kemungkinan stack overflow saat memproses dataset berukuran besar. Node baru
disisipkan dengan membandingkan nilai epoch-nya terhadap setiap node yang ditemui,
bergerak ke cabang kiri jika lebih kecil atau sama, dan ke cabang kanan jika lebih
besar.

Dalam pengujian benchmark, data yang dimasukkan ke BST terlebih dahulu diacak
menggunakan std::shuffle dengan seed tetap (mt19937(42)). Hal ini dilakukan untuk
mencegah degenerasi pohon menjadi struktur linear akibat data yang sudah terurut
secara monoton, yang akan menyebabkan kompleksitas waktu turun ke O(n).

b.  Operasi Range Query (O(log n + k))

Pencarian rentang waktu merupakan operasi unggulan BST dalam sistem ini. Fungsi
rangeQuery melakukan pruning cabang secara cerdas: jika epoch suatu node lebih kecil
dari batas awal pencarian, seluruh subpohon kirinya dilewati; jika epoch lebih besar
dari batas akhir, seluruh subpohon kanannya dilewati. Hanya cabang yang berpotensi
mengandung node dalam rentang yang ditelusuri, sehingga jumlah node yang dikunjungi
jauh lebih sedikit dibanding traversal penuh. Di sini k merepresentasikan jumlah
hasil yang ditemukan.

c.  Operasi Delete dan Rekonstruksi Seimbang (O(n))

Penghapusan log usang pada BST dilakukan dalam tiga tahap:

    (1) collectBefore — traversal inorder mengumpulkan semua node dengan epoch lebih
        besar atau sama dengan nilai cutoff ke dalam sebuah vector terurut.
    (2) destroyTree — seluruh pohon lama dihapus dari memori.
    (3) buildBalancedFromSorted — pohon baru dibangun kembali secara seimbang dari
        vector hasil pengumpulan menggunakan teknik rekursif berbasis elemen tengah
        array (divide and conquer). Teknik ini menjamin tinggi pohon tetap minimal
        (≈ log₂ n) sehingga performa pencarian berikutnya tidak terdegradasi.


4.1.3  Hash Table (LogHashTable)

Hash Table diimplementasikan menggunakan std::unordered_map dari STL C++ sebagai
backbone, dengan teknik separate chaining: setiap slot (bucket) menyimpan
std::vector<LogEntry> yang menampung seluruh entri log dengan kunci yang sama.

Sistem menjalankan dua instansi Hash Table secara paralel di dalam LogManager:
instansi ht_level menggunakan field level sebagai kunci, dan instansi ht_module
menggunakan field module sebagai kunci. Dengan demikian, pencarian berdasarkan level
maupun modul masing-masing dapat dilayani dalam kompleksitas konstan.

a.  Operasi Insert (O(1) amortized)

Setiap log baru ditambahkan ke vector bucket yang sesuai dengan kuncinya. Jika
bucket untuk kunci tersebut belum ada, std::unordered_map secara otomatis
membuatnya. Kompleksitas rata-rata operasi ini adalah O(1) secara amortized.

b.  Operasi Search (O(1) + O(k))

Pencarian berdasarkan kunci merupakan operasi paling efisien dalam sistem ini. Hash
lookup ke bucket yang tepat dilakukan dalam O(1), kemudian seluruh isi bucket
dikembalikan dalam O(k) di mana k adalah jumlah log dalam bucket tersebut. Untuk
kategori seperti level "ERROR" yang memiliki jumlah entri terbatas relatif terhadap
total data, operasi ini sangat cepat.

c.  Operasi Delete (O(n))

Penghapusan log usang menggunakan idiom erase-remove_if pada setiap bucket secara
berurutan. Predicate lambda memeriksa apakah epoch setiap entri lebih kecil dari
nilai cutoff. Seluruh elemen yang memenuhi kondisi tersebut dihapus dari vector
bucket secara efisien dalam satu kali pass.

d.  Operasi Statistik (O(B))

Karena data sudah terkelompok dalam bucket berdasarkan kunci, statistik per-kategori
dapat diperoleh hanya dengan membaca ukuran setiap bucket tanpa perlu menelusuri
seluruh elemen. B merepresentasikan jumlah bucket unik (jumlah level atau modul yang
berbeda), yang jauh lebih kecil dari total n entri log.


Tabel 4.1  Ringkasan Kompleksitas Operasi Ketiga Struktur Data

+-----------------+-------------------+-------------------+-------------------+
| Operasi         | Linked List       | BST               | Hash Table        |
+-----------------+-------------------+-------------------+-------------------+
| Insert          | O(1)              | O(log n)          | O(1) amortized    |
| Search by key   | O(n)              | O(n)              | O(1) + O(k)       |
| Search by range | O(n)              | O(log n + k)      | O(n)              |
| Delete          | O(n)              | O(n)              | O(n)              |
| Statistik       | O(n)              | -                 | O(B)              |
+-----------------+-------------------+-------------------+-------------------+


4.2  Mekanisme Penyimpanan File

4.2.1  Format File CSV

Sistem menggunakan format CSV (Comma-Separated Values) sebagai media penyimpanan
data log secara persisten. Setiap baris dalam file merepresentasikan satu entri log
dengan lima kolom yang dipisahkan oleh tanda koma, yaitu: log_id, timestamp (dengan
format YYYY-MM-DD HH:MM:SS), level, module, dan message.

4.2.2  Mekanisme Pembacaan (Read)

Pembacaan file CSV dilakukan melalui fungsi loadCSV() yang terdapat pada modul
LogManager. Fungsi ini membuka file menggunakan std::ifstream, melewati baris header
pertama, kemudian memproses setiap baris secara streaming dengan std::getline dan
std::istringstream untuk memisahkan kolom berdasarkan delimiter koma.

Proses pembacaan menerapkan beberapa mekanisme sanitasi data, antara lain:
penghapusan karakter carriage return (\r) dari akhir field message yang muncul pada
file berformat Windows (CRLF), pembersihan tanda kutip ganda yang membungkus pesan
yang mengandung koma, serta penolakan baris dengan log_id kosong. Fungsi ini juga
menerima parameter limit opsional yang membatasi jumlah baris yang dibaca, berguna
untuk mode sampling pada pengujian benchmark.

4.2.3  Mekanisme Penulisan (Write)

Penulisan ke file CSV dilakukan melalui fungsi exportBenchmarkToCSV() yang terdapat
pada modul main. Fungsi ini menulis hasil pengujian benchmark ke dalam file
benchmark_results.csv menggunakan std::ofstream, dengan header kolom dan setiap
baris hasil diformat menggunakan fixed dan setprecision(4) untuk presisi empat angka
di belakang koma. File hasil ini selanjutnya dibaca oleh modul visualisasi berbasis
web untuk ditampilkan dalam bentuk grafik interaktif.

4.2.4  Pipeline Alur Data

Data mengalir dalam sistem mengikuti pipeline berikut: file CSV dibaca oleh
loadCSV() dan dikonversi menjadi vector of LogEntry, kemudian setiap entri
didistribusikan ke empat struktur data oleh LogManager::insertLog(). Setelah
benchmark dijalankan, hasilnya diekspor kembali ke format CSV melalui
exportBenchmarkToCSV(), yang kemudian dikonsumsi oleh dashboard visualisasi web
untuk ditampilkan sebagai grafik.


4.3  Penjelasan Modul Penting

4.3.1  Modul LogEntry

LogEntry merupakan struct yang berfungsi sebagai model data dasar dari seluruh
sistem. Setiap entri log direpresentasikan oleh satu objek LogEntry yang memiliki
lima field utama: log_id, timestamp, level, module, dan message. Selain itu, terdapat
satu field tambahan bertipe long long bernama _epoch yang dideklarasikan dengan
kata kunci mutable.

Fungsi toEpoch() pada struct ini mengimplementasikan teknik lazy evaluation: konversi
string timestamp ke nilai integer Unix epoch hanya dilakukan satu kali untuk setiap
objek, kemudian hasilnya disimpan dalam field _epoch sebagai cache. Pada pemanggilan
berikutnya, nilai cache langsung dikembalikan tanpa melakukan konversi ulang. Teknik
ini sangat penting untuk menjaga efisiensi, mengingat toEpoch() dipanggil berulang
kali selama operasi pencarian, perbandingan, dan pengurutan. Penggunaan kata kunci
mutable memungkinkan field _epoch dimodifikasi meskipun fungsi toEpoch() dideklarasi
sebagai const.

4.3.2  Modul LogManager

LogManager merupakan kelas orkestrator yang menjadi inti dari seluruh sistem. Ia
menerapkan pola desain Facade dengan menyembunyikan kompleksitas pengelolaan empat
struktur data di balik satu antarmuka tunggal. Keempat struktur data yang dikelola
adalah: satu instansi LogLinkedList (ll), satu instansi LogBST (bst), satu instansi
LogHashTable berindeks level (ht_level), dan satu instansi LogHashTable berindeks
modul (ht_module).

Fungsi insertLog() mendistribusikan setiap log baru ke keempat struktur sekaligus
dalam satu pemanggilan. LogManager juga bertanggung jawab mengarahkan setiap jenis
query ke struktur data yang paling optimal: pencarian berbasis level dan modul
diarahkan ke Hash Table untuk memanfaatkan lookup O(1), pencarian berbasis rentang
waktu diarahkan ke BST untuk memanfaatkan kemampuan range query-nya, serta operasi
statistik diarahkan ke Hash Table berindeks level karena data sudah terkelompok per
kategori.

Operasi penghapusan log usang (deleteBefore) dilaksanakan secara tersinkronisasi
pada keempat struktur data sekaligus untuk mencegah inkonsistensi data antar
struktur.

4.3.3  Modul Benchmark

Modul benchmark terdapat dalam fungsi runBenchmark() pada kelas LogManager. Modul
ini dirancang untuk menghasilkan perbandingan yang adil dan dapat direproduksi
(reproducible) antar ketiga struktur data. Untuk setiap ukuran dataset n dalam
kumpulan {1.000, 3.000, 5.000, 10.000}, setiap struktur data diuji pada empat
skenario operasi: insert, pencarian eksak, pencarian rentang waktu, dan penghapusan.

Beberapa mekanisme khusus diterapkan untuk memastikan keadilan pengujian. Pertama,
semua struktur diuji pada sampel data yang identik. Kedua, data yang dimasukkan ke
BST diacak terlebih dahulu menggunakan std::shuffle dengan seed tetap mt19937(42)
untuk mencegah degenerasi pohon sekaligus memastikan hasil yang konsisten di setiap
pengulangan eksekusi. Ketiga, rentang waktu untuk skenario range search ditetapkan
seragam selama 7 hari dari timestamp pertama dataset.

Pengukuran waktu menggunakan std::chrono::high_resolution_clock yang memberikan
presisi pengukuran di tingkat milidetik dengan resolusi tertinggi yang tersedia pada
platform eksekusi.

4.3.4  Modul Visualisasi Web

Modul visualisasi merupakan aplikasi web terpisah yang terdapat dalam folder
visualnya/. Aplikasi ini dibangun menggunakan Vite sebagai bundler dan dev server,
Plotly.js untuk rendering grafik interaktif, serta PapaParse untuk melakukan parsing
file benchmark_results.csv di sisi browser.

Dashboard menampilkan empat grafik utama yang merepresentasikan perbandingan
performa operasi insert, pencarian eksak, pencarian rentang waktu, dan penghapusan
data. Grafik kelima menampilkan kurva skalabilitas komparatif untuk semua operasi
secara bersamaan. Untuk menjalankan modul ini, pengguna perlu mengeksekusi perintah
npm run dev di dalam folder visualnya/ dan mengakses alamat http://localhost:5173/
melalui browser.

4.3.5  Generator Dataset (generate.py)

File generate.py merupakan script Python yang digunakan untuk membangkitkan dataset
log sintetis dalam format CSV. Script ini menghasilkan hingga 100.000 record log
dengan distribusi acak yang merata pada lima kategori level (INFO, WARNING, ERROR,
DEBUG, CRITICAL), sepuluh modul sistem, dua puluh jenis pesan log, dan timestamp
yang tersebar acak sepanjang tahun 2025. Dataset yang dihasilkan menjadi input utama
program C++ melalui fungsi loadCSV() untuk keperluan pengujian dan benchmark.
